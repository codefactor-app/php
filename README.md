# Codefactor для PHP

Codefactor — локальный статический анализатор, который помогает находить сложный код, дублирование и проблемы в зависимостях до рефакторинга и ревью. Этот пакет устанавливает консольную команду через Composer для работы в вашем проекте.

Анализатор поддерживает PHP, Python, Rust, JavaScript и TypeScript: выбор пакета определяет способ установки, а не список доступных языков. Исходный код анализируется локально, не исполняется и не отправляется во внешний сервис.

## Что даёт анализ

| Задача | Что вы получаете |
| --- | --- |
| Найти места для рефакторинга | Размер функций и файлов, число параметров, вложенность, цикломатическая и когнитивная сложность, замечания с файлами и строками |
| Разобраться в незнакомом проекте | Графы вызовов, зависимости между каталогами и модулями, переходы к исходникам в локальном веб-интерфейсе |
| Проверить структуру проекта | Поиск дублирования, циклов зависимостей и нарушений заданных границ архитектурных слоёв |
| Оценить потенциально дорогой код | Статические оценки роста числа операций при увеличении размера входных данных |
| Контролировать изменения | Настраиваемые пороги, отчёты для ревью и CI, baseline для работы с существующими замечаниями |

После `scan` вы видите сводку проекта, метрики и замечания с уровнем, расположением и нарушенным порогом. Это помогает выбрать участок для проверки и сравнивать изменения по одним критериям.

## Установка

Пакет [codefactor/codefactor](https://packagist.org/packages/codefactor/codefactor) доступен в Packagist.

Нужны PHP >=8.1 с OpenSSL, включённый `allow_url_fopen`, Composer >=2.2 и проект с `composer.json`.

```sh
composer require --dev codefactor/codefactor
```

При первой установке Composer спросит, разрешить ли плагин `codefactor/codefactor`. Ответьте `y`: плагин автоматически скачает анализатор, а Composer сохранит разрешение в `composer.json`.

Пакет устанавливается как dev-зависимость проекта; команда появляется в `vendor/bin`. Закоммитьте `composer.json` и `composer.lock`, чтобы остальные участники и CI могли выполнить `composer install` с теми же настройками.

Альтернативный способ запуска: `composer exec -- codefactor scan .`.

При установке выбирается последний стабильный бинарь анализатора из [GitHub Releases](https://github.com/codefactor-app/core/releases), проверяются размер и SHA-256. Поддерживаются Linux, macOS и Windows на x64 и ARM64. Для скачивания нужен доступ к GitHub; токен не требуется. После установки команды работают без сети.

## Быстрый старт

Из корня проекта выполните:

```sh
./vendor/bin/codefactor --version
./vendor/bin/codefactor scan .
```

Для первого запуска конфигурация не нужна. Лучше анализировать корень проекта, чтобы учитывать метаданные импортов и зависимостей, а область анализа ограничивать через YAML.

Чтобы увидеть все замечания и сохранить отчёт:

```sh
./vendor/bin/codefactor scan . --all
./vendor/bin/codefactor scan . --format json --out codefactor-report.json
```

Консоль по умолчанию показывает до 50 замечаний. `--all` снимает это ограничение; экспортируемый JSON всегда содержит полный отчёт. Коды завершения помогают отличить найденные нарушения от сбоя команды — таблица приведена в разделе CI.

## Конфигурация проекта

Создайте `analyzer.yaml` в корне проекта. Например, для PHP:

```yaml
config_version: 1
languages:
  enabled: [php]
paths:
  include: ["**"]
  exclude:
    - "**/test/**"
    - "**/tests/**"
    - "**/Tests/**"
    - "**/spec/**"
    - "**/fixtures/**"
    - "**/Fixtures/**"
    - "**/*Test.php"
    - "**/generated/**"
    - "**/migrations/**"
vendor:
  paths: ["vendor/**", "**/vendor/**", "node_modules/**"]
  mode: collapsed
  parse: lazy
limits:
  file_lines: {warn: 400, error: 800}
  function_lines: {warn: 40, error: 100}
  functions_per_file: {warn: 20, error: 40}
  methods_per_class: {warn: 15, error: 30}
  function_params: {warn: 4, error: 7}
  cyclomatic_complexity: {warn: 10, error: 20}
  types_per_file: {warn: 1, error: 3}
  module_cycle: {warn: 0}
architecture:
  enabled: true
  profile: strict
cache:
  enabled: true
  path: .analyzer-cache
output:
  formats: [console]
```

Этот пример не привязан к фреймворку: он анализирует файлы выбранных языков, исключает тесты, миграции и сгенерированные файлы, задаёт пороги предупреждений `warn` и ошибок `error`. Порог `types_per_file` следит за правилом PSR-4 «один класс на файл», `module_cycle` показывает циклы между namespace. Пути считаются от корня анализа, globs чувствительны к регистру. Правила `.gitignore` тоже учитываются; для анализа тестов удалите соответствующие исключения. Каталоги зависимостей отмечены отдельно и могут раскрываться при анализе связей.

Проверьте настройки и выполните анализ:

```sh
./vendor/bin/codefactor config check --file analyzer.yaml --strict
./vendor/bin/codefactor scan . --config analyzer.yaml --strict-config
./vendor/bin/codefactor config show --file analyzer.yaml --resolved
```

`scan .` автоматически находит `analyzer.yaml` или `analyzer.yml`. При анализе другого корня, например `scan ./src`, указывайте файл явно: `--config analyzer.yaml`. Параметры CLI имеют приоритет над YAML, YAML — над настройками по умолчанию.

### Готовые профили

| Профиль | Когда использовать |
| --- | --- |
| [minimal.yaml](examples/config/minimal.yaml) | Выбрать язык и начать с настроек по умолчанию |
| [medium.yaml](examples/config/medium.yaml) | Настроить исключения, основные пороги и кеш для ежедневной работы |
| [maximum.yaml](examples/config/maximum.yaml) | Настроить пороги для разных участков проекта, слои, наборы и расширенный анализ |
| [symfony.yaml](examples/config/symfony.yaml) | Приложение на Symfony: исключения, слои и внешние вызовы по раскладке `symfony/skeleton` |
| [laravel.yaml](examples/config/laravel.yaml) | Приложение на Laravel: исключения, слои и фасады по раскладке `laravel/laravel` |

```sh
cp vendor/codefactor/codefactor/examples/config/medium.yaml analyzer.yaml
```

Каждый пример самодостаточен. Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку или CMS; в `maximum` пути слоёв, имена сущностей и каталоги сторонних библиотек служат примерами — замените их на свои. Профили `symfony` и `laravel` описывают слои по стандартным каталогам этих фреймворков и подстраиваются под проект переименованием селекторов. Профиль `minimal` выбирает язык, сохраняя остальные настройки по умолчанию, включая архитектурный и алгоритмический анализ.

[Как выбрать и применить профиль](examples/README.md) · [Полный справочник YAML](docs/configuration.md). Доступные ключи установленной версии также показывает `./vendor/bin/codefactor config keys`.

## Изучение проекта в браузере

```sh
./vendor/bin/codefactor serve . --port 8080 --open --watch
```

Откройте `http://127.0.0.1:8080/`, если браузер не открылся автоматически. В интерфейсе доступны исходники с замечаниями, карта кода, графы вызовов, зависимости, архитектурные проверки и действующие критерии анализа. `--watch` обновляет анализ при изменении исходников; остановка — `Ctrl+C`. После редактирования YAML перезапустите сервер.

Сервер по умолчанию доступен только с этого компьютера. Если меняете `--host`, учитывайте, что подключённые пользователи получают доступ к исходникам анализируемого проекта.

## Полезные команды

```sh
./vendor/bin/codefactor metrics . --group-by directory
./vendor/bin/codefactor relations --a 'dir:src' --b 'dir:tests' --format md
./vendor/bin/codefactor external list --category db
./vendor/bin/codefactor --help
./vendor/bin/codefactor scan --help
```

`metrics` сравнивает показатели по группам; `relations` показывает вызовы между выбранными частями проекта; `external` перечисляет распознанные внешние операции. Замените `src` и `tests` на каталоги своего проекта. Для подробного графа вызовов используйте `./vendor/bin/codefactor graph --help` или откройте нужную функцию в веб-интерфейсе.

## Отчёты и CI

| Формат `scan` | Для чего использовать |
| --- | --- |
| `console` | Чтение результатов в терминале |
| `json` | Сохранение полного отчёта и дальнейшая обработка |
| `md` | Отчёт для ревью и документации |
| `sarif` | Передача замечаний в инструменты статического анализа |

```sh
composer install --no-interaction --prefer-dist
./vendor/bin/codefactor config check --file analyzer.yaml --strict
./vendor/bin/codefactor scan . --strict-config --fail-on-warn --format sarif --out codefactor.sarif
```

На этапе анализа устанавливайте dev-зависимости и оставляйте плагины включёнными. `--no-plugins` отключает установку анализатора; обычный `composer install` восстанавливает её. `--no-scripts` поддерживается.

Сохраняйте `codefactor.sarif` как артефакт CI. Для JSON замените формат на `json` и имя файла на `codefactor-report.json`. Логи идут в stderr отдельно от отчёта.

| Код завершения | Значение |
| --- | --- |
| `0` | Нет блокирующих замечаний |
| `1` | Предупреждения при `--fail-on-warn` либо ошибка выполнения команды |
| `2` | Найдены ошибки правил анализа |
| `3` | Синтаксическая ошибка YAML в основном файле конфигурации |

Без `--fail-on-warn` обычные предупреждения не блокируют проверку. Архитектурные замечания носят рекомендательный характер и не меняют код завершения, в том числе с `--fail-on-warn`: нарушения границ слоёв читайте из отчёта `sarif` или `json`. Чтобы цикл между namespace блокировал проверку, задайте порог `limits.module_cycle`: в профилях `medium`, `symfony` и `laravel` он даёт предупреждение, в `maximum` — ошибку. При ошибке команды читайте stderr и диагностику отчёта.

### Подключение к существующему проекту

Если в проекте уже много замечаний, после проверки первого отчёта создайте baseline:

```sh
./vendor/bin/codefactor baseline create --root . --config analyzer.yaml
./vendor/bin/codefactor scan . --strict-config --fail-on-warn
```

Baseline сохраняет текущие замечания в `.analyzer-baseline.json` и подавляет их в последующих проверках, чтобы выделить новые. Проверьте файл и закоммитьте вместе с `analyzer.yaml`. В `.gitignore` добавьте `.analyzer-cache/` и создаваемые отчёты.

## Обновление

```sh
composer install
./vendor/bin/codefactor --version
```

Каждый `composer install` и `composer update` проверяет последний стабильный релиз анализатора, даже если PHP-пакет не изменился. При каждой установке запрашивается свежий манифест `latest`; совпадающий по размеру и SHA-256 бинарь повторно не скачивается. `composer.lock` фиксирует PHP-пакет, но не фиксирует версию анализатора. `composer dump-autoload` не обращается к сети.

## Если что-то не работает

- **Composer блокирует плагин:** выполните `composer config allow-plugins.codefactor/codefactor true`, затем `composer install`.
- **Команда не найдена:** используйте `./vendor/bin/codefactor` из корня проекта и убедитесь, что dev-зависимости установлены.
- **Бинарь отсутствует:** повторите `composer install` с разрешённым плагином.
- **Ошибка HTTPS:** проверьте OpenSSL, `allow_url_fopen`, доступ к GitHub и настройки сертификатов.
- **Настройки не применяются:** запускайте из корня проекта или передайте `--config analyzer.yaml`; используйте `config check --strict` и `config show --resolved`.
- **Нужна установка через корпоративное зеркало:** `CODEFACTOR_RELEASE_BASE_URL` задаёт HTTPS-адрес зеркала, `CODEFACTOR_CA_BUNDLE` — доверенный сертификат. `CODEFACTOR_BINARY` позволяет использовать уже скачанный бинарь нужной платформы вместо сетевой загрузки.

## Как читать результаты

Статический анализ может не определить часть динамических вызовов, рефлексии и метапрограммирования. Оценки алгоритмической сложности описывают рост числа операций, а не измеренное время выполнения. Проверяйте диагностику разбора и определения связей; отсутствие замечания не доказывает отсутствие проблемы. Дополнительные архитектурные гипотезы профиля `extended` требуют проверки человеком.
