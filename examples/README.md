# Конфигурация Codefactor для PHP

Выберите профиль и сохраните его в своём проекте. Все YAML самостоятельные: дополнительные файлы для `include` не нужны.

| Профиль | Для чего подходит |
| --- | --- |
| [minimal.yaml](config/minimal.yaml) | Выбрать язык и использовать остальные настройки по умолчанию |
| [medium.yaml](config/medium.yaml) | Задать исключения, основные и структурные пороги, зависимости и кеш |
| [maximum.yaml](config/maximum.yaml) | Настроить дополнительные метрики, слои, наборы и отдельные пороги для участков проекта |
| [symfony.yaml](config/symfony.yaml) | Приложение на Symfony: исключения `var/`, `migrations/`, слои `controller → service → repository → entity`, внешние вызовы HttpClient, Messenger, Mailer |
| [laravel.yaml](config/laravel.yaml) | Приложение на Laravel: исключения `storage/`, `database/`, `bootstrap/cache/`, слои `http → application → models`, фасады `Http`, `DB`, `Queue` |

Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку или CMS и подходят любому Composer-проекту. Профили `symfony` и `laravel` берут за основу `medium` и добавляют каталоги, слои, переопределения порогов и внешние вызовы стандартной раскладки фреймворка; каталог, которого нет в проекте, просто не даёт совпадений.

## Применить профиль

Если пакет установлен, скопируйте профиль из его каталога:

```sh
cp vendor/codefactor/codefactor/examples/config/medium.yaml analyzer.yaml
```

Из корня анализируемого проекта:

```sh
./vendor/bin/codefactor config check --file analyzer.yaml --strict
./vendor/bin/codefactor scan . --config analyzer.yaml --strict-config
./vendor/bin/codefactor config show --file analyzer.yaml --resolved
```

## Адаптировать под свой проект

- `languages.enabled` определяет языки анализа; пакет поддерживает все пять языков Codefactor.
- `paths.include: ["**"]` включает поддерживаемые файлы, в том числе файлы в корне. Средний и расширенный профили исключают тесты, сгенерированный код и типовые артефакты. Уберите нужные исключения, если хотите анализировать эти файлы.
- Правила `.gitignore` также учитываются. Зависимости выделены через `vendor.paths`, чтобы изучать их связи отдельно от метрик проекта.
- Globs чувствительны к регистру: `**/tests/**` не исключает `Tests/` из бандлов, поэтому профили перечисляют оба написания.
- `limits` задаёт уровни предупреждений `warn` и ошибок `error`. Подберите пороги для своего проекта, затем проверьте их через `config check --strict`. `limits.by_language` нужен только проектам с несколькими языками: для единственного языка он молча перекрывает общий порог.
- Контроллеры, сущности Doctrine и модели Eloquent по замыслу содержат независимые методы, поэтому профили фреймворков поднимают для них `lcom4`, `methods_per_class` и `function_params` через `limits.by_path`.
- В расширенном профиле и профилях фреймворков пути слоёв, полные имена сущностей, сторонние библиотеки и каталоги старого кода — примеры для замены. `architecture.composition_roots` действует, только если файл сборки попадает в селектор слоя.

Минимальный профиль сохраняет архитектурный и алгоритмический анализ по умолчанию. `scan .` автоматически находит `analyzer.yaml` или `analyzer.yml`; для `scan ./src` передавайте файл явно: `--config analyzer.yaml`. После изменения YAML перезапустите локальный веб-интерфейс.

Добавьте `analyzer.yaml` в репозиторий проекта, а `.analyzer-cache/` — в `.gitignore`.

## Контроль структуры в CI

Архитектурные находки `arch_cycle` и `arch_boundary` не меняют код завершения даже с `--fail-on-warn`. Для блокировки используйте числовые пороги: `limits.module_cycle: {warn: 0}` в `medium`, `symfony` и `laravel` превращает цикл между namespace в предупреждение, которое останавливает проверку с `--fail-on-warn`; `{error: 0}` в `maximum` даёт код завершения `2` без флага. Нарушения запрещённых зависимостей между слоями читайте из отчёта `--format sarif` или `--format json`.
